# План развития: управление сессиями и прозрачная комиссия

## Текущее состояние

Сетевое ядро — экспериментальный прозрачный ретранслятор BTC Stratum V1. `stratum_session.py` управляет жизненным циклом подключения, `upstream_manager.py` выбирает исходящий адрес для нового подключения, `router.py` передаёт байты, `observer.py` пассивно считает наблюдаемые события. `dashboard_server.py` обслуживает локальную панель, `proxy.py` — точка входа. Код комиссии и управление пулами не подключены к рабочему потоку.

`devfee_scheduler.py` — **изолированная модель**, а не действующий DevFee. Тест `tests/test_two_pool_lab.py` проверяет 990 и 10 искусственных валидных шар для двух различных пулов с разными `extranonce1` и учётными данными после явного переподключения симулированного клиента. Это не тест автоматического распределения комиссии, бесшовного переключения или выплаты 1% дохода.

## Очерёдность

1. **Модель протокола и сеансов.** Явные состояния подписки/авторизации/заданий; раздельные контексты каждой сессии, difficulty и extranonce; согласование `mining.configure` по [BIP 310](https://github.com/bitcoin/bips/blob/master/bip-0310.mediawiki). Проверять нестандартный порядок, дубликаты ID и версии прошивок. Сначала сосуществовать с прозрачным режимом, а не незаметно менять его.
2. **Контролируемый failover.** Тестировать `mining.extranonce.subscribe` и `mining.set_extranonce` для каждой комбинации ASIC/пула. Если устройство не подтвердило возможность смены extranonce, применять явно описанное переподключение. Не обещать сохранение TCP-сессии и нулевые потери всем устройствам; отделять старые задания и ответы от нового upstream.
3. **DevFee.** Исследовать same-pool multi-authorize индивидуально для каждого пула: подмена имени сама по себе не доказывает зачисление работы другому аккаунту. Для cross-pool проверять связанные сессии, extranonce, difficulty, version rolling и изоляцию job ID. Старая шара может передаваться только породившему её upstream, если задача ещё действительна; в противном случае показывать неопределённость/отказ. Тестировать отказ комиссии с продолжением работы клиента без скрытого долга. Solo и merged mining — отдельные модели рисков.
4. **Проверка SHA-256d.** Построить полный валидатор заголовка по job/coinbase/merkle/extranonce, ntime, nonce и согласованным version bits. Применять верный target к конкретной работе. Защита от дубликатов должна учитывать границы сеанса, задания, version bits, размер памяти и истечение записей. Ошибка локальной проверки не должна приводить к потере настоящего блока. `lab/pow.py` сейчас не является готовым валидатором Stratum.
5. **Отчётность.** Учёт сложности только по однозначно сопоставленным ответам пула и соответствующему заданию; отдельные категории rejected и unknown. Показать период, ограничения, перезапуски и округление, экспорт с защитой приватности. Отдельно измерять время ответа пула и наблюдаемые задержки ASIC; не называть их полноценным сетевым ping без корректного метода. Количество шар и короткое окно не доказывают ровно 1% денежных выплат.
6. **Администрирование фермой.** Группы и маршруты, понятная пользователю смена пула/кошелька, отдельные секреты для каждого пула и проверка отката. Перед API записи — аутентификация, роли, CSRF-защита, ограничение запросов, аудит изменений и атомарное хранение. Не создавать управляющие кнопки без работающего и защищённого backend.
7. **Проверка перед реальным использованием.** Фаззинг, длительные и нагрузочные проверки, обе стороны TLS, тесты зависших соединений и half-close, независимая проверка безопасности, матрица моделей/прошивок/пулов и согласованный пилот на реальных ASIC.

## Ограничения обещаний

Доля времени, сложность принятых шар и фактические денежные выплаты — разные величины. Случайные шары, vardiff и переключения дают отклонения на конечных интервалах. Нельзя гарантировать точные 1,00% каждой выплаты без поддерживаемого пулом механизма расчётов; нельзя гарантировать нулевые stale shares, бесшовность для всех ASIC и время ответа менее 1 мс без проверки. Оптимистичное подтверждение шары рискованно: локально верная шара может быть отклонена пулом. Такой режим не реализован и не должен маскироваться под подтверждение пула.
